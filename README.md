# SystemKeeper

Self-hosted сервис бекапов и мониторинга для своих серверов и баз данных. Ставится одной командой, обновляется кнопкой в интерфейсе, бесплатный и открытый ([MIT](LICENSE)).

## Что умеет

- **Бекапы файлов серверов по SSH** — выбор каталогов в обзоре файлов, исключения, команда перед бекапом (например, дамп), сжатие на стороне сервера, контрольные суммы SHA-256 у каждого файла бекапа.
- **Бекапы баз MySQL/MariaDB, PostgreSQL и ClickHouse** — целиком или выбранные базы и таблицы, у части таблиц — только структура; для MySQL и PostgreSQL — автонастройка отдельного пользователя для бекапов.
- **Куда сохранять** — встроенный диск SystemKeeper, Яндекс Диск и любые S3-совместимые хранилища (AWS, Yandex Object Storage, Selectel, MinIO…), сразу в несколько мест; подключили новое хранилище — все прежние бекапы копируются в него одной кнопкой.
- **Сколько хранить** — число последних копий и лимит объёма для каждого источника; самая свежая копия не удаляется никогда.
- **Ручное восстановление без SystemKeeper** — рядом с бекапами в хранилище лежат `README.md`, `index.json` и `backup.json` с описанием каждого бекапа и командами восстановления.
- **Расписание** — cron-выражение у каждого сервера и базы (в часовом поясе `BACKUP_TIMEZONE`, по умолчанию Europe/Moscow); планировщик проверяет его каждую минуту; запуск, пропущенный из-за обновления или простоя, выполняется позже, если с его времени прошло не больше 6 часов. Плюс ручной запуск кнопкой, через API или по секретной ссылке-хуку из CI/CD.
- **Проекты и группы** — серверы и базы собраны по проектам, меню и страницы хранения — по ним же.
- **Мониторинг** — доступность (HTTP(S), TCP, ping и DNS-проверки по расписанию, uptime за 24 ч / 7 / 30 дней, история сбоев) и ресурсы серверов (CPU, память, диски, сеть, нагрузка — по SSH, без агента на сервере, графики до 30 дней).
- **Алерты** — правила на CPU, память, диски, нагрузку, недоступность сервера и сайта, срок сертификата, неудачные и пропущенные бекапы, заполнение хранилища; условие должно продержаться заданное время, напоминания, пока не решено, и сообщение о решении. Каналы — Telegram, почта и вебхук с подписью HMAC; почту и доступ к Telegram (адрес Bot API, прокси) администратор настраивает в интерфейсе.
- **API-first** — всё, что есть в интерфейсе, доступно через JSON API ([docs/api.md](docs/api.md), OpenAPI на `/api/docs`).

## Установка на сервер

Нужен Linux-сервер с root-доступом; Docker поставится сам, если его нет.

```sh
curl -fsSL https://github.com/DrTiget/SystemKeeper/releases/latest/download/install.sh | sudo sh
```

Установщик разворачивает сервис в `/opt/systemkeeper`, генерирует `.env` (ключ шифрования `APP_KEY`, пароли базы), запускает контейнеры и создаёт администратора: спросит email и выведет пароль. Повторный запуск безопасен — настройки и данные сохраняются. Переменные: `SK_DIR` (каталог), `SK_PORT` (порт, по умолчанию 8080), `SK_VERSION` (версия, по умолчанию последняя), `SK_ADMIN_EMAIL`.

**Сохраните копию `/opt/systemkeeper/.env`**: `APP_KEY` шифрует пароли, SSH-ключи и доступы к облакам в базе — без него их не восстановить.

Что где лежит в `/opt/systemkeeper`: `data/storage` — локальные бекапы и файлы приложения, `data/mysql` — база, `backups/` — дампы базы перед обновлениями (три последних), `state/` — связь с обновлятором.

Команда `systemkeeper` на сервере: `update [vX.Y.Z]`, `status`, `logs [сервис]`, `admin` (ещё один администратор), `up`, `down`.

### Обновления

Сервер проверяет новые релизы раз в 10 минут (`SK_UPDATE_CHECK=false` — не проверять). Администратор видит в меню «Доступна vX.Y.Z» и обновляется одной кнопкой; то же — `systemkeeper update`. Обновление выполняет контейнер `updater`:

1. пока идут бекапы или синхронизация хранилищ, кнопка недоступна; с момента запроса новые бекапы не начинаются (пропущенные плановые запустятся сразу после обновления, стоящие в очереди ждут его конца), а обновлятор дожидается уже идущих;
2. делает дамп базы;
3. скачивает `compose.yaml` релиза, меняет `SK_VERSION` и перезапускает сервисы — миграции применяются при старте;
4. если новая версия не поднялась за 5 минут — возвращает прежнюю версию и восстанавливает базу из дампа.

`updater` — единственный контейнер с доступом к Docker; портов наружу у него нет, а веб-приложение лишь кладёт в общий каталог запрос `{"version": "…"}`.

## Уведомления

Алерты уходят в каналы Telegram, почту и вебхук. Подключение настраивает администратор в интерфейсе — **Настройки → Уведомления** (в `.env` лазить не нужно):

- **Почта (SMTP)** — сервер, порт, шифрование (STARTTLS, SSL/TLS или без), логин и пароль, адрес и имя отправителя; кнопка «Отправить тестовое письмо». Если SMTP в настройках не задан, письма идут через `MAIL_*` из `.env`; по умолчанию там `MAIL_MAILER=log` — письма никуда не уходят, и канал «Почта» создать нельзя, пока почта не настроена.
- **Telegram** — адрес Bot API (по умолчанию `https://api.telegram.org`) и HTTP- или SOCKS5-прокси с логином и паролем: с серверов в РФ Telegram часто недоступен напрямую. Кнопка «Проверить соединение» проверяет доступность адреса через прокси.

Пароли хранятся в базе в зашифрованном виде и в интерфейсе и API не показываются; пустое поле пароля при сохранении оставляет прежний. Токен бота и чат задаются в самом канале (**Алерты → Каналы**). Подробности — в [docs/api.md](docs/api.md).

## Разработка

Laravel 13, PHP 8.5, MySQL 8.4, очереди `database`; фронтенд — Vue 3 + TypeScript + Tailwind v4 в `frontend/`. Правила для разработчиков и ИИ-агентов — [AGENTS.md](AGENTS.md).

```sh
cp .env.example .env
UID=$(id -u) GID=$(id -g) docker compose up -d --build
docker compose exec app composer install
docker compose exec app php artisan key:generate
docker compose exec app php artisan migrate
docker compose exec app php artisan user:create
docker compose exec app php artisan test
```

### Фронтенд

SPA в каталоге `frontend/`: Vue 3, TypeScript, Vite, vue-router, pinia, Tailwind CSS v4. Дизайн — по `docs/design-system/` (токены подключены в `frontend/src/styles/app.css`).

Запуск (сервис `frontend` в `compose.yaml`, dev-сервер Vite):

```sh
docker compose up -d frontend   # npm install и vite на порту FRONTEND_PORT (по умолчанию 5173)
```

Откройте `http://localhost:${FRONTEND_PORT:-5173}`. Запросы `/api` проксируются на `http://nginx:80`. Токен хранится в `localStorage`; без токена или при `401` от API происходит переход на `/login`. Проверка типов: `docker compose exec frontend npm run typecheck`; сборка: `docker compose exec frontend npm run build`.

### Выпуск релиза

```sh
git tag v1.2.3 && git push origin v1.2.3
```

Перед тегом добавьте раздел версии в [CHANGELOG.md](CHANGELOG.md) (`## v1.2.3 — ГГГГ-ММ-ДД`) — он станет описанием релиза и попадёт в окно «Что нового» в приложении. GitHub Actions (`.github/workflows/release.yml`) соберёт образ `ghcr.io/drtiget/systemkeeper` для amd64 и arm64 (теги версии и `latest`) и создаст релиз с файлами `compose.yaml`, `install.sh`, `updater.sh` из `deploy/`. Прод-образ — `docker/prod/Dockerfile`: nginx + php-fpm, собранный фронтенд, роли контейнера `web`, `queue`, `backups`, `scheduler`.
